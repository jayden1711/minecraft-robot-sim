## C1. "It's just a game."

Answer: the game is the editor and the display. The learning problem is a standard MuJoCo robot-learning problem; the game only supplies geometry
and task markers, and the viewer. Nothing about the learning depends on Minecraft being present.

Test (M3): train and evaluate with a scene exported to MJCF; delete the Minecraft server and mod from the machine's path; run `rollout.py` from the exported bundle
on 20 held-out seeds. Pass = it runs and reports success rate with the same seeds as the in-game run. M0 half: `tests/test_critiques.py::test_C2_*`
already runs the exported scene with only `mujoco` and `numpy` importable (`python -I`).

## C2. "Minecraft physics is fake."

Answer: it is not used. Minecraft's physics (gravity, collision, entities) never touches a robot. MuJoCo simulates everything; Minecraft only provides block positions.

Test (runs now): export the demo maze through the server code path to an MJCF file; run a seeded rollout in a separate isolated Python process
(`python -I`, no `mcrobot` importable, no sockets) twice: the trajectory hashes must be bit-identical, differ for a different seed (non-vacuous), and equal the in-process rollout.
`server/tests/test_critiques.py::test_C2_*`. Repeat at M3 on the trained-policy rollout with the Minecraft server process not running (check with `pgrep`, recorded in the run log).

## C3. "Blocks aren't real terrain."

Answer: blocks are a coarse, editable, shareable terrain format; they are exact for what they claim (axis-aligned boxes at known scale), and the robot only sees
MuJoCo geometry. They are also not the end state: M4 rebuilds a real room to scale and runs on a real rover, which is the test of whether block-built worlds transfer.

Tests:
1. (runs now) Geometry fidelity: the exported collision boxes cover exactly the solid cells (disjoint, exact), partial blocks keep their real sub-block boxes, and the coordinate mapping is a rotation with a round trip. `test_boxes.py`, `test_scene.py`.
2. (M2) Seam sensitivity: train/evaluate Go2 on the same terrain with merged boxes vs one box per block; report the gap in success and in contact-force spikes. If seams hurt, merge differently or fillet edges.
3. (M2) Scale: same world at two `meters_per_block` values; policy success vs step height is reported, not assumed.
4. (M4) Real-vs-sim: the room rebuilt from measurements, rover run on the real floor; success sim vs real, with the gap stated.

## C4. "Toy tasks."

Answer: M1 is a toy by design (reach a goal in a maze) because it proves the pipeline. The point is the pipeline and what it allows next. We do not claim more than we measure.

Tests: each milestone has a pre-stated held-out evaluation, defined before training:
- M1: 50 mazes the policy never saw (player-built plus randomly generated by the same exporter), success rate over seeds with confidence intervals; a straight-line-to-goal baseline and a random policy for scale.
- M2: terrain families with increasing step height; report where Go2 and G1 stop succeeding, including the failures.
- M4: a task on the real rover in the real room.
"Toy" is then a statement about difficulty with numbers behind it, not a label.

## C5. "It's just a scripted animation."

Answer: every ghost pose shown in game is a logged env state from the training run (PLAN.md, Ghosts), and the final policy replays in plain MuJoCo on held-out seeds.

Tests (M1):
1. Provenance: `ghost_log.npz` is written by the sender (every sample sent, with step and env id). For a sampled (step, env) the check re-derives the pose from the training checkpoint at that step with the same seed and compares to the logged pose within tolerance; a scripted animation cannot do this.
2. Learning is real: ghost success fraction from the log rises over training and is not time-based; a run with the reward zeroed (control) must not rise.
3. Held-out replay: load `policy` + `scene.xml` in plain MuJoCo (no mcrobot, no Minecraft), run N seeds never used in training, success rate with seeds recorded; per-seed trajectories must reproduce bit-identically across two runs.
4. Frame check: in-game screenshot of ghosts at step t and the MuJoCo render of the logged states at step t show the same positions in the same world.
`test_C5_ghosts_are_logged_training_states` is a placeholder (skipped) until M1 produces training logs.

## C6. "The ghost you watch might not be what the simulator is doing" (display failures, stale ghosts)

Answer: a ghost that is invisible, frozen or left over from an earlier run is a display fault, and the mod now makes it loud instead of silent.

What went wrong once: a first mod build wrote `block_state` in a form that 26.3 decodes to air, the invisible entities were saved in the world, and a later build reused them by UUID, so the demo ran but showed nothing. Controls now in place (mod, tested in `GhostCommandsTest`, `BridgeReconnectTest` and the smoke test `scripts/smoke_server.sh`):
1. Every streaming session gets its own tag and UUIDs; the first spawn removes all existing ghost entities; a ghost entity that loads outside a session (saved in an unloaded chunk) is discarded on load; stop, trainer loss and server shutdown remove them, so none stay in the world save.
2. After summoning, the mod reads every part back from the server and reports an ERROR in the log and in chat if a part is missing or reads back as air.
3. Spawn, stop (with the reason), and a 30-second heartbeat (poses received, age of the last pose) are logged, so a frozen or stalled stream is visible.
4. The bridge reconnects by itself when the trainer restarts and says only "connected" or "disconnected".
Limit: the read-back proves the entities exist with a non-air block; that the poses match the simulator is still the C5 provenance test.

## Honest limits (stated up front)

- Everything is simulation. A policy that works here may not work on a robot; M4 measures that, and until then no real-robot claim is made.
- Minecraft is proprietary (Mojang EULA). The project ships no Minecraft code or assets; users supply their own copy.
- Blocks are coarse. Terrain finer than a block (or a tenth of a block with the scale option) is out of scope.
